# gpu-watch-gui

`tools/gpu-watch.sh`（端末の TUI）を小さな GTK4 の常駐ウィンドウにしたもの。グラフは出さない。
数値だけを「項目名 / 現在値 / 60 秒最大」の並びで表示する。

センサーの読み取りはこのツールでは行わない。`gpu-watch.sh -o raw` を子プロセスとして起動し、
その出力（`INFO` / `HOST` / `FAN` / `GPU` 行）を読んで表示するだけ。取得元（RAPL・coretemp・
fan journal の所在解決）は gpu-watch.sh に 1 本化してある。「取れない値は n/a、推測で埋めない」
という扱いも gpu-watch.sh と同じ。

書き込みは「ファン補正スライダー」（A30 ファンの自動カーブへの加減）だけ。後述。
描画は GL を使わない（Cairo）。窓が固まった原因が GL レンダラーだったため（「ハングの診断」）。
もう 1 つ、PC 全体の電力だけは Tapo プラグ（P110M）の実測を読める（任意。「PC 全体の実測（Tapo）」）。

## 依存

portal と同じく **依存ゼロ・venv なし**。システムの `/usr/bin/python3` + `python3-gi`（GTK 4.0）を
そのまま使う。`model.py`（raw 行の解析・窓内の最大/平均・しきい値超過の edge 検出）は GTK を
import しない純 Python。GTK を import するのは `app.py` だけ。

例外が Tapo 用の専用 venv（`~/.local/share/tapo-meter/.venv`、`tapo` 0.11.1 だけを入れる）。
`setup-tapo.sh` が作る（sudo 不要・冪等）。GUI 本体はシステムの python3 のまま動き、
この venv は読み取り役 `tapo_power.py` を子プロセスで動かすためだけに使う。無ければ Tapo の機能だけが使えない。

## 起動

```bash
tools/gpu-watch-gui/run-gpu-watch-gui
```

`run-gpu-watch-gui` は窓の python を見張り、**窓が固まった（終了コード 75）・強制終了された（137 など）ときは
5 秒後に起動し直す**。起動し直さないのは、終了コード 0（窓を閉じた・SIGTERM）、30 秒未満で終わったとき
（起動直後の失敗で回り続けない）、スクリプト自身が SIGTERM/SIGINT/SIGHUP を受けたとき。
止めたままにするなら、窓を閉じるか、`pkill -f run-gpu-watch-gui` でスクリプトを先に止める（窓の python だけを
`kill -KILL` すると起動し直される）。

`-n`・`-w`・`-t`・`-T`・`-i`・`-F`・`-P` を受け付ける。意味と既定値は `gpu-watch.sh -h` と同じで、
そのまま子プロセスに渡す。

```
-n SEC   サンプリング間隔（秒）。既定 1
-w SEC   窓内最大の対象期間（秒）。既定 60
-t DEG   GPU 温度アラートのしきい値（摂氏）。既定 80
-T DEG   CPU 温度アラートのしきい値（摂氏）。既定 90
-i IDX   監視する GPU。nvidia-smi -i と同じ書式。既定は全 GPU
-F UNIT  ファン PWM を読む systemd ユニット。既定 a30-fan.service。off で非表示
-P WATT  筐体ベースライン（W）。省略すると推定は出さない
--psu-efficiency RATIO  PC 全体(推定)で使う電源ユニット効率（0 より大きく 1 以下）。既定 0.90
--app-id ID             GLib アプリケーション ID。試験で別インスタンスを起動するためのもの
--fan-offset-file PATH  ファン補正値を書くファイル。既定 ~/.local/state/a30-fan/offset.json
                        （fan_host.py が読む場所）。試験の別インスタンスが本番の補正を消さないよう分けるためのもの
--fan-preference-file PATH  スライダーの前回の値を保存するファイル。既定 state/fan-offset.json。
                        試験の別インスタンスが本番の保存値を書き換えないよう分けるためのもの
--tapo auto|off         PC 全体の実測に Tapo を使う。auto は起動 1 秒後に、保存したログインで自動ログインする
                        （保存が無ければログイン画面を出す）。既定 auto
--tapo-host IP          ログイン画面の IP の初期値。省略すると前回入力した値
--tapo-python PATH      tapo を入れた専用 venv の python。既定 ~/.local/share/tapo-meter/.venv/bin/python
--tapo-interval SEC     Tapo の読み取り間隔（秒、2 以上）。既定 5
```

## 表示する値

- **HOST**: CPU 使用率、CPU 温度、メモリ（使用 GiB / 全体 GiB、%）、CPU 電力、PSys 電力、
  PC 全体電力（Tapo の実測。取れていないときは推定で、値の頭に `≈` が付く）
- **GPU**（GPU ごとに 1 ブロック）: 温度、使用率、VRAM（使用 MiB / 全体 MiB）、電力
- **FAN**: Pico H への PWM 指令値（%）とモード。stale（ログが古い）・none（ログが無い）のときは
  n/a にし、現在値のセルにマウスを乗せると理由が出る（gpu-watch.sh のコメント参照）
- 最下行: 最終更新時刻。子プロセスが（原因を問わず）落ちたら「停止中: 理由」を表示し、
  5 秒後に自動で再起動を試みる

## ファン補正スライダー

ファンの行の下の「補正 +N」の行。A30 ファンの**自動カーブ**に -50〜+50（%ポイント）を足し引きする。
右の「0」ボタンで 0 に戻す。実際に出る PWM は、その上の「ファン」の行（journal の指令値）で確認する。
`-F off`（ファンの行を出さない）のときはスライダーも出ない。

- **意味**: 目標 PWM = 自動カーブの値 + スライダーの値。結果は 30〜100% に収める（30 は Pico 側の下限）。
  例: カーブが 45%（GPU 38℃）のとき、+20 なら 65%、-50 なら下限の 30%。
  下げるときは 1 回の更新で最大 2 ポイントずつ下がる（`fan_host.py` の既存の制限。上げるのは即時）
- **高温の保護**: GPU 70℃ 以上では、下げ側（マイナス）の補正を `fan_host.py` が無視してカーブ通りにする。
  上げ側（プラス）は有効。70℃ は暫定値で、A30 の公式の上限ではない。GUI は温度を見ず、判断は `fan_host.py` だけが行う
- **有効期限**: GUI が動いている間だけ有効。補正が 0 以外の間、GUI が 1 秒ごとにファイルを書き直し、
  `fan_host.py` は `updated` が約 10 秒より古いファイルを無視して補正 0（自動カーブ）に戻す。
  窓を閉じる・終了要求を受けるとファイルを消す。GUI が落ちても約 10 秒で自動に戻る。
  補正が 0 のときはファイルを置かない
- **起動時に前回の値へ戻る**: スライダーの値は `state/fan-offset.json`（git 管理外、権限 600、
  `{"version": 1, "offset": N}`）に保存する。動かすと 1 秒以内の tick で書き（ドラッグ中に何度も書かない）、閉じるときにも書く。
  起動すると、この値でスライダーを始め、最初の tick で上の補正ファイルを書く。再起動しても保たれる。
  無い・壊れているときは 0。窓を閉じている間と、GUI が動いていない間は 0（自動）で、保存値は残る
- **受け渡し**: `fan_host.py` は Pico のシリアルポートを排他で開くので、GUI から Pico には話せない。
  代わりに `~/.local/state/a30-fan/offset.json`（ディレクトリ 0700・ファイル 0600）を介す。
  書き込みは一時ファイル→rename（`gpu_watch_gui/fan_offset.py`）。形式:
  `{"version": 1, "offset": <整数 -50..50>, "updated": <epoch 秒>}`
- **相手側**: `~/Proj/SettingThisMachine/FanControl/electronic-circuit/a30_pico_ubuntu/pc/fan_host.py` の
  `read_offset` / `apply_offset`。ファイル形式を変えるときは、この README・`fan_offset.py`・`fan_host.py`・
  両方のテスト（同じ JSON の見本文字列を置いてある）を揃える
- **反映に必要な操作**: `fan_host.py` を変更したので、`a30-fan.service` の再起動（`sudo systemctl restart a30-fan.service`）が要る。
  再起動の間（止める時の全速指令と、再起動後の最初の 3 秒）だけファンは 100% になる。
  GUI は、開いたままの窓を閉じて `run-gpu-watch-gui` で起動し直す（開いたままだと新しい窓は作られず、既存の窓が前面に出るだけ）
- ファイルを書けないとき（権限・容量など）は、最下行に「ファン補正を書けません: 理由」を出す。窓は落ちない
- `fan_host.py` が止まっている・補正を読まない版のときも、スライダーは動くが効果は出ない（ファンの行の PWM が変わらない）

## PC 全体の実測（Tapo）

「PC 全体」の行は、Tapo スマートプラグ（P110M）が測る**コンセント側の電力**（電源ユニットの損失を含む）を出す。
実測が出ているときは値の頭に `≈` が付かない。マウスを乗せると、実測であることの説明が出る（固定の文。
毎秒変わる数値は入れない。経緯は「ハングの診断」）。

### 初回と、2 回目以降

1. `tools/gpu-watch-gui/setup-tapo.sh` で専用 venv を作る（1 回だけ）。
2. **初回**: GPU Watch を起動すると、約 1 秒後に**ログイン画面**が自動で開く。プラグの IP・TP-Link ID
   （メールアドレス。Google のパスワードではない）・パスワードを入れて「ログイン」。後からは最下行の「Tapo」ボタンでも開ける。
   「この PC に保存する（再起動後も自動でログイン）」のチェックは既定でオン。
3. **2 回目以降（再起動後も）**: 保存してあれば、起動すると**ログイン画面を出さずに**自動でログインする。
   前回の IP（`state/tapo.json`）へ、`state/tapo.cred` を TPM で復号した ID とパスワードでログインする。
4. 「あとで」を押すと、実測は出さず推定のままになる。

**パスワードの置き場所。**
- 入力した値は GPU Watch のメモリに置き、読み取り役 `tapo_power.py` には**標準入力**（1 行の JSON）で渡す。
  ファイル・環境変数・コマンドライン引数には出さない。`state/tapo.json` に残すのは IP とメールアドレスだけ
  （権限 600、git 管理外）。`~/.config/tapo-meter/credentials` のような資格情報ファイルは作らない。
- 「保存する」を選んだときだけ、**この PC の TPM 2.0 に封印（暗号化）して `state/tapo.cred`** に置く
  （`gpu_watch_gui/tapo_vault.py`、`systemd-creds encrypt --with-key=tpm2`。権限 600、git 管理外）。
  `tapo` ライブラリはパスワードでしかログインできず、トークンでの再ログインができないため、保存するのはパスワード自体になる。
  封印するのは TP-Link ID とパスワードの JSON で、標準入力で渡す（コマンドライン引数・環境変数・一時ファイルには出さない）。
  暗号は AES-256-GCM で、鍵は TPM が持ち、ディスクには残らない。**この PC の TPM でしか復号できない。**
- **守れるもの**: ディスクのイメージ、ホームのコピー、バックアップからパスワードを読まれること。
  **守れないもの**: mt で動く他のプロセスが TPM に復号を頼むこと（人の入力なしで復号できる以上、避けられない）。
  Secure Boot が無効なので、この PC で別の OS を起動して復号されること。
- **キーリングは使わない。** このマシンの login キーリングは RDP の自動ログインのためにパスワードが空
  （`knowledge/10-silver/areas/rdp-session.md`）で、保存すると暗号化されずに書かれるため。
- **前提**: mt が `/dev/tpmrm0`（所有者 tss:tss、0660）を開けること。**初回だけ `sudo usermod -aG tss mt` を実行して、
  再ログイン（または再起動）する。** 開けないときは、ログイン画面の保存チェックが無効になり、ツールチップに直し方が出る。
- 既定で PCR 7（Secure Boot の設定）にも縛られる（`--tpm2-pcrs` を省略したときの systemd-creds の既定）。
  BIOS の設定やファームウェアを変えて復号できなくなったら、理由つきでログイン画面を出す。保存分は消さないので、
  入力し直して「保存する」でログインすれば置き換わる。
- 保存を取り消すには、ログイン画面で**チェックを外してログイン**する（`state/tapo.cred` を消す）。
- 保存するのは**最初の実測が 1 回取れてから**。打ち間違えたパスワードを残さないため。封印した直後に復号して
  元と一致することを確かめ、合わなければ暗号文を消してステータスに理由を出す。
- TPM の呼び出し（実測で封印 約 2.4 秒、復号 約 1.8 秒。2026-11-03）は別スレッドで行い、窓を止めない。
- Windows 版（`TapoPlug.exe`）も同じ考え方で、資格情報を DPAPI で暗号化した `tapo-credential.xml` に保存し、
  起動のたびにそれを復号して毎回ログインする（同じユーザー・同じ PC でしか復号できない）。ここでは DPAPI の代わりに TPM を使う。

### 仕組みと失敗時の動き

- 読み取り役は `tapo_power.py --raw`（専用 venv の python、`-I`）。5 秒ごとに `TAPO, 時刻, W` の行を出し、
  GUI が `model.py` で解析する。機器へのログインは読み取り役が行う。電源の ON/OFF は送らない。
- P110M(JP) の暗号方式は **TPAP**。python-kasa 0.12.0 は未対応のため、`tapo`（PyPI）を使う。
  機器の探索は IP を指定した UDP（ポート 20002）。
- **最初の 1 回が読めなかったとき**（IP の誤り・ID/パスワードの誤り・機器に届かない）は、誤ったパスワードの
  連続試行で機器側に制限されるのを避けるため、自動の再試行を絞る。ログイン失敗と機器に届かないことは区別していない
  （理由の文は読み取り役の最後のエラー行）。
  - ログイン画面から入力したとき: 再試行せず、パスワードをメモリから消して、理由つきでログイン画面を出し直す。
  - **保存分を復号して取った資格情報での自動ログイン**のとき: 起動直後はネットワークがまだ使えないことがあるので、
    30 秒・60 秒・120 秒の間隔で最大 3 回だけ試し直す（`tapo_feed.AUTO_LOGIN_RETRY_DELAYS_SEC`）。
    使い切ったらログイン画面を出す。**保存分は消さない**（一時的な停電や機器の不在で消さないため）。
- 一度読めた後に失敗したときは、読み取り役が機器を探し直しながら続ける。GUI 側は最後の値を 20 秒だけ保持し、
  それより古くなったら実測を出さず推定に戻す（古い数字を現在値として見せない）。
- 読み取り役が落ちたら 5 秒後に同じ資格情報で起動し直す。

### 実測と推定のずれ（2026-11-01 の実測）

実測 196 W（GPU 約 89 W・CPU 使用率 約 50%）のとき、推定式の値は ≈284〜298 W で、約 90〜100 W 高かった。
原因は未確定。有力な仮説は「PSys がすでに dGPU の電力を含んでいて、GPU を二重に足している」（下の式の注記と食い違う）。
根拠は、PSys の較正値（約 175 W）が CPU 65 W + GPU 約 89 W + 周辺 約 20 W にほぼ一致すること。
ただし較正時の GPU 負荷を記録していないため確定できない。直すなら、較正で GPU の電力も記録して PSys から引き、
式の GPU 加算は残す形になる（再較正が要る）。

## CPU 電力・PSys・PC 全体の電力（実測 と 推定）

Intel RAPL の `energy_uj` は既定で root 専用（CVE-2020-8694 の緩和。**この緩和は外さない**）。
そのため非 root で常駐するこの GUI は、RAPL が読める環境でだけ実測の「CPU 電力(実測)」
「PSys(実測)」を出し、読めない環境では較正データから推定した「CPU 電力(推定)」
「PSys(推定)」を出す。実測と推定は値を混同しないよう、必ず項目名に `(実測)`/`(推定)` を
付けて区別する。較正していなければ「未較正」と出し、推測値で埋めない。

### 較正の仕組み

`constraint_*_power_limit_uw` と `constraint_*_time_window_us`（PL1 の上限電力・時定数）は
RAPL の `energy_uj` と違って**一般ユーザーでも読める**。これと「CPU 負荷段階ごとに実測した
消費電力」を組み合わせて、負荷率から電力を推定する。

1. ウィンドウの「電力を較正」ボタンを押すと、`pkexec` 経由で `calibrate-power.py` を root で
   起動する（パスワード入力は pkexec のグラフィカルなダイアログで行う。このリポジトリの
   コードからは sudo/pkexec を呼ばない。較正スクリプト自身は root 専用で、非 root では
   終了コード 2 になる）。
2. `calibrate-power.py` は CPU 負荷を 0% / 25% / 50% / 75% / 100%（スレッド数換算）の
   5 段階に変え、各段階で「2 秒ならし → 5 秒計測 → 5 秒休み」してから、CPU 使用率・
   package-0 の電力・psys の電力（無ければ null）を測る。休みを挟むのは、PL1 の移動平均が
   前の段階の高負荷で絞られたまま次の段階に引き継がれるのを避けるため。
3. 結果の JSON を `tools/gpu-watch-gui/state/calibration.json`（git 管理外。機械ごとの実測値
   のため）に一時ファイル→rename で保存し、即座に表示へ反映する。

### 推定の式

- **CPU 電力(推定)**: 較正点（util, cpu_w）を CPU 使用率で区間線形補間し、範囲外は端の値で
  止める。さらに PL1 頭打ちを「推定値の指数移動平均（時定数 = 較正した PL1 の
  `time_window_us`）が PL1 以上になったら、以後の推定値を PL1 以下に抑える」という形で模す。
  これにより高負荷が始まった直後の短時間は PL2 相当で PL1 を超えた値を出し、負荷が続くと
  PL1 に収束する。
- **PSys(推定)**: psys_w も同様に補間し、CPU が PL1 頭打ちで抑えられた分
  （補間した cpu_w − 抑えた後の cpu_w）を差し引く（PSys は CPU を含むプラットフォーム
  全体の電力のため）。
- **PC 全体(推定)** = (PSys 推定 + GPU 実測電力の合計) ÷ PSU 効率。GPU が 1 基でも n/a なら
  全体も n/a にする（片方だけで埋めない）。PSU 効率の既定 0.90 は実測していない仮定値
  （`--psu-efficiency` で上書きできる）。PSys は SoC プラットフォームの電力で dGPU の消費電力を
  含まないため、GPU 実測をそのまま足す設計にしている。

較正していない、または較正時と CPU が違う（CPU を載せ替えた等）ときは、これらの行に
「未較正」と出す。項目名の横のツールチップに式・較正日時・上記の仮定を出す。

色は CSS クラスで付ける（見出しや他のラベルには付けない。現在値のセルだけ）。
温度は gpu-watch.sh の `temp_color` と同じしきい値（しきい値以上=赤、しきい値-10 以上=黄、
それ未満=緑）。使用率は `load_color` と同じ（90%以上=赤、70%以上=黄）。
しきい値を決めていない項目（VRAM・電力・ファン PWM）は普通の文字色にする。
灰色は「n/a」「未較正」など**値が取れていない**ときだけに使う。

## ハングの診断

窓が固まったときの診断と自動復旧は `gpu_watch_gui/hang_watchdog.py`（GTK 非依存）が行う。
1 秒ごとの tick で `beat()` を呼び、別スレッドで見張る。

- **30 秒途切れたら**（`HANG_EXIT_SEC`）: `state/hang-traceback.log`（git 管理外・追記）に、Python の全スレッドのスタックと、
  `gdb` があれば C のスタックを書いて、**終了コード 75** で終わる。再起動は `run-gpu-watch-gui` が行う（5 秒後）。
  ログには起動のたびに `---- 起動 時刻 pid=`、ハング検出のたびに `---- ハング検出 …` の行が入る。
- **C のスタックは自分に付けた gdb で採る**（`gdb -p <自分の pid> -batch -nx -ex 'set debuginfod enabled off' -ex 'thread apply all bt'`）。
  `ptrace_scope=1` では子の gdb が親に付けないので、`prctl(PR_SET_PTRACER, gdb の pid)` でその gdb だけに許す。
  出力はパイプではなくログファイルへ直接書かせる（gdb が付いている間は全スレッドが止まり、パイプだと詰まるため）。
  60 秒で打ち切る。`bt full`（局所変数を出す）とコアの書き出しはしない。
- **最後の砦**: 見張りのスレッド自身が GIL を取れないときのために、`faulthandler.dump_traceback_later(120, exit=True)` を
  beat のたびに掛け直す。120 秒 beat が無ければ Python のスタックを書いてプロセスを終了する（終了コード 1）。
- **終了後**: 子プロセス（`gpu-watch.sh`・`tapo_power.py`）は、親が死ぬと出力パイプが閉じて数秒で終わる
  （2026-11-03 の実測では 4 秒以内。起動し直しの 5 秒より短い）。
- 書くのは関数名・行番号・アドレスだけで、値（パスワードなど）は含まない。
- 固まった窓を手で調べるときは、終了させる前に `kill -USR1 <pid>`（`pgrep -f gpu_watch_gui.app` で pid を調べる）で
  Python のスタックを同じファイルへ書ける。C のスタックを手で採るなら、別の端末で
  `sudo gdb -p <pid> -batch -nx -ex 'set debuginfod enabled off' -ex 'thread apply all bt' > /tmp/gpu-watch-bt.txt 2>&1`
  （sudo のパスワードを聞かれる。スタックを読むだけで、メモリの中身は書き出さない）。
- 固まった窓を `SIGKILL` で終わらせるとコアダンプは作られない。`SIGABRT` などでコアを出すと、メモリ上のパスワードが
  ディスクに残るおそれがあるので使わない。

### 2026-11-03 のハングの原因（gdb で確定）

再起動後の自動起動で動いていた窓が、約 2 分後（17:01:22）に固まった。Python のスタックは `Gio.Application.run` だけで、
Python のコールバックの中ではなかった。C のスタックでは、メインスレッドが
`g_main_context_iteration → フレームクロックの paint → gsk_renderer_render（libgtk-4）→ libgallium（Mesa 25.2.8、Intel iris）→ futex`
で待ち続けていた（Mesa の他のスレッドは待機中）。**GTK 4.14 の GL レンダラーが Mesa のドライバの中で止まっている**。

- 対策: `app.py` の先頭で `GSK_RENDERER=cairo`・`GDK_DEBUG=gl-disable` を設定し、GL を使わずに描く（ソフトウェア描画。
  窓は小さく更新も 1 秒ごとなので負荷は問題にならない）。`setdefault` なので、環境変数で GL に戻して比べられる。
  実機で、GL 関連の共有ライブラリ（libgallium・libEGL_mesa・libEGL_nvidia）と GL 用のスレッド（gdrv0 など）が
  読み込まれないことを確認した。Mesa 自体の不具合は直していない。
- 2026-11-01 の最初のハング（Tapo にログインして約 5 分後）は、スタックを取れておらず原因は未確定。同じ GL の問題だった
  可能性が高いが、確認はできていない。このとき「ツールチップに毎秒変わる数値を入れたため」と疑って「PC 全体」のツールチップを
  固定文にしたが、2026-11-03 のハングの原因とは別だった（固定文のままにしてある）。
- 「ハングしても自動で立ち直る」仕組み（上）は、原因が別だった場合の保険。

## 通知

GPU 温度が `-t`、CPU 温度が `-T` を**超えた瞬間だけ** `notify-send -u critical` で 1 回出す
（gpu-watch.sh の `-b edge` と同じ考え方）。しきい値以下に戻ると解除され、次に超えたときまた出る。
`notify-send` が無い・失敗しても GUI 自体は落ちない。

## 終了・二重起動

ウィンドウを閉じると子プロセス（`gpu-watch.sh -o raw`）に SIGTERM を送って終了する。
プロセスは残らない（`pgrep -af 'gpu-watch.sh -o raw'` で確認できる）。

二重起動は `Gtk.Application`（アプリ ID `jp.localai.GpuWatchGui`）の一意性で防ぐ。2 回目の起動は
新しい窓を作らず、既存の窓を前面に出す。

`run-gpu-watch-gui` から起動した窓は、窓を閉じる（終了コード 0）と起動し直されない。ハング・強制終了では起動し直される
（「起動」を参照）。

## 自動起動（ログイン時）

```bash
tools/gpu-watch-gui/install-autostart.sh              # 登録
tools/gpu-watch-gui/install-autostart.sh --uninstall  # 解除
```

`~/.config/autostart/gpu-watch-gui.desktop` を生成する（GNOME の仕様で autostart の登録ファイルは
ここにしか置けないため、本体はリポジトリ内に置いたまま、登録ファイル 1 個だけをここに作る）。
冪等（何度実行しても結果は同じ）。有効にするには再ログイン（または再起動）が要る。

`.desktop` の `Exec` は `run-gpu-watch-gui`（窓の python を見張って、固まったら起動し直す bash）。
再起動後は、Tapo は保存したログインで自動でログインし、ファン補正も前回の値に戻る。

`.desktop` には `X-GNOME-Autostart-Delay=5` を付けてある。自動ログイン直後は
`lock-after-autologin.desktop` が画面をロックする想定で、ロック解除後にはこのウィンドウが
既に表示されている状態になる。

## Wayland の制約

このマシンは GNOME / Wayland（`XDG_CURRENT_DESKTOP=ubuntu:GNOME`）。Wayland では通常のアプリから
ウィンドウの位置や「常に最前面」を指定できない。そのため、このウィンドウにはタイトルバーを
付けてあり、利用者が自分で動かせるようにしてある。

## 試験

```bash
uvx --with pytest pytest tools/gpu-watch-gui/tests/test_units.py -q
```

`model.py`（raw 行の解析、n/a の扱い、窓内の最大・平均、edge 検出、較正データの検証、
Tapo の行の解析と鮮度の判定、
区間線形補間、PL1 頭打ち、電力推定の式）と、`calibrate-power.py` の純関数（root 不要の部分
だけ。energy_uj の巻き戻り補正、負荷段階のスレッド数算出）、`gpu-watch.sh -o` の引数検証、
`fan_offset.py`（補正値の丸め・原子的な書き込み・権限・取り下げ・ファイル形式の見本）を
確認する。Tapo まわりは、`tapo_power.py` の資格情報の受け取り（標準入力の JSON・エラー文にパスワードを載せない・
不備のときの終了コード）、`tapo_feed.py` の保存物（IP とメールアドレスだけで、パスワードを保存できない作り）を見る。
GTK は import しない（スライダー行・ログイン画面の組み立ては GTK が要るので、この試験では見ていない）。
`tapo` 本体と実機の Tapo は試験では使わない。

ほかに次を見る。
- `fan_offset.py` の保存値（書いて読むと同じ・無い/壊れている/NaN は 0・範囲外は丸める・権限 600・失敗時に一時ファイルを残さない）。
- `tapo_feed.auto_login_retry_delay`（30・60・120 秒で、使い切ったら None）。
- `tapo_vault.py`（`systemd-creds` を偽物に差し替えて見る。本物の TPM は試験では使わない）: コマンドラインが TPM だけの鍵・固定の名前・
  標準入力→標準出力であること、パスワードが引数に出ないこと、ディスクの暗号文に平文が無いこと・権限 600、
  封印直後の確認が合わなければ暗号文を消すこと、失敗時のメッセージにパスワードを載せないこと、
  保存が無ければ None・復号できなければ理由つきの例外、使えない理由（コマンドが無い・TPM を開けない）の案内。
- `hang_watchdog.py`: gdb のコマンドライン（`-batch`・`-nx`・debuginfod 無効・`bt full` を使わない）、拍動と途切れの判定、
  ハング時のログと終了コード 75、本物のスレッドが途切れを検出して拍動中は終了しないこと、ログを開けなくても落ちないこと、
  最後の砦のタイマーが gdb の待ち時間より長いこと。
- `run-gpu-watch-gui`（偽の `gpu_watch_gui.app` を置いて実行。待ち時間は環境変数 `GPU_WATCH_GUI_MIN_RUN_SEC` /
  `GPU_WATCH_GUI_RESTART_DELAY_SEC` で縮める）: 75 で終わったら起動し直す・0 で終わったら起動し直さない・
  起動直後の失敗で回り続けない・SIGTERM を窓へ渡して起動し直さない・整数以外の値を拒否する。

実 GTK でしか確かめられないこと（ログイン画面の保存チェック、保存・自動ログイン・保存取り消し、
ファン補正の復元、GL を使っていないこと、ハングの検出と終了コード 75）は、使い捨てのスクリプトで確かめた
（ダミーのアカウントと偽の読み取り役で Tapo の行を流した。本番の `state/` と補正ファイルは触っていない）。
TPM は、`tss` グループに入った後に `sg tss` で本物を使って確かめた: 封印→復号が一致する・暗号文を 1 バイト壊すと
復号が拒否される・暗号文に平文が無い・権限 600、さらに GUI で「保存→再起動相当の自動ログイン」が通る
（読み取り役へ ID とパスワードが正しく渡る）。
実機の Tapo への自動ログインと、再起動をまたいだ復元は、利用者が確かめる。

`calibrate-power.py` は root 専用（RAPL の `energy_uj` を読むため）。試験は非 root で実行して
終了コード 2 になることだけを確認し、実際の較正（root・pkexec・パスワード入力が要る）は
試験では行わない。実機での較正は GUI の「電力を較正」ボタンから利用者が行う。
